    Deployment¶

    Deploying KeyLease is a short, strictly ordered sequence of stellar contract commands against a Stellar network. Steps 2–5 each depend on the previous one, so the whole thing is scripted:

    SOURCE_ACCOUNT=keylease-admin ./scripts/deploy-testnet.sh

    To create and fund the identity as well (Testnet only):

    KEYLEASE_GENERATE_KEY=1 SOURCE_ACCOUNT=keylease-admin ./scripts/deploy-testnet.sh

    The script never deploys mock_token. That token has an unlimited mint and is for tests and local sandboxes only.

    Dry run¶

    --dry-run resolves every default, validates every input and prints each command with the values it would send, then exits. It builds nothing, signs nothing and makes no network call:

    ./scripts/deploy-testnet.sh --dry-run
ADMIN=G... PROVIDER=G... TOKEN=C... ./scripts/deploy-testnet.sh --dry-run

    Values that only exist after a real deployment — the contract id, the service id, the Wasm hash — are printed as <placeholders>. Input that a real run would reject fails here first: a malformed ENDPOINT_HASH, a non-numeric RATE_PER_CALL, or a missing or malformed REGISTRY in an upgrade mode. The same flag works for every mode, so --upgrade --dry-run shows the upload and proposal without queueing anything.

    Mainnet guard¶

    NETWORK is user-controlled, so a typo or an exported variable can point the script at mainnet. Mainnet deployment is deferred until the contract is audited (see Mainnet), so the script refuses NETWORK=mainnet unless KEYLEASE_ALLOW_MAINNET=1 is exported for that invocation:

    KEYLEASE_ALLOW_MAINNET=1 NETWORK=mainnet ./scripts/deploy-testnet.sh --dry-run

    In every mode the script prints a banner with the resolved network, mode and signing identity before the first send, adds a MAINNET — real XLM is at risk line when the opt-in is set, and repeats the network in the final summary.

    What the script does¶

    1. cargo build --target wasm32v1-none --release --all
2. stellar contract deploy   <registry wasm>  -> REGISTRY contract id
3. stellar contract invoke -- init            --admin  <ADMIN>
4. stellar contract invoke -- set_token       --admin <ADMIN> --token <TOKEN>
5. stellar contract invoke -- register_service --provider <P> \
                              --rate_per_call <R> --endpoint_hash <H>

    Then it re-reads get_service to confirm the write landed, and prints a block you can paste into .env. In deploy mode that block is nine lines:

    KEYLEASE_CONTRACT_ID=C...
KEYLEASE_SERVICE_ID=1
KEYLEASE_TOKEN_ADDRESS=C...
KEYLEASE_NETWORK=testnet
KEYLEASE_RPC_URL=https://soroban-testnet.stellar.org
KEYLEASE_ADMIN=G...
KEYLEASE_PROVIDER=G...
KEYLEASE_RATE_PER_CALL=1000000
KEYLEASE_ENDPOINT_HASH=<64 hex chars>

    In --upgrade mode it prints only the two lines that change — KEYLEASE_CONTRACT_ID (unchanged, echoed back for confirmation) and KEYLEASE_NETWORK — plus the new version() and Wasm hash, which are not env entries.

    Mapping printed values to your env file¶

    Two sets of names are in play and mixing them up is the usual way a deployment goes sideways. The variables in Configuration are inputs: you set them before running the script, they carry no KEYLEASE_ prefix, and SOURCE_ACCOUNT is the only one that touches a key. The KEYLEASE_* lines the script prints are outputs: they describe what now exists on the ledger, and they are what your client, indexer or CI reads afterwards.

    Printed as .env entry What it actually is In .env?
    KEYLEASE_CONTRACT_ID KEYLEASE_CONTRACT_ID the deployed KeyLeaseRegistry id; the script asserts it matches ^C[A-Z0-9]{55}$ public
    KEYLEASE_SERVICE_ID KEYLEASE_SERVICE_ID the decimal u64 returned by register_service; monotonic from 1 public
    KEYLEASE_TOKEN_ADDRESS KEYLEASE_TOKEN_ADDRESS the SEP-41 escrow token set by set_token — for native this is the network's SAC id, so it is the same string on every Testnet deployment public
    KEYLEASE_NETWORK KEYLEASE_NETWORK the CLI network name; also the --network argument for every later invocation public
    KEYLEASE_RPC_URL KEYLEASE_RPC_URL Testnet only: the script hardcodes https://soroban-testnet.stellar.org and prints the placeholder <your <network> RPC url> for anything else. Replace the placeholder — do not paste it public
    KEYLEASE_ADMIN KEYLEASE_ADMIN address authorized for set_token and upgrade; defaults to the address of SOURCE_ACCOUNT public address, secret seed elsewhere
    KEYLEASE_PROVIDER KEYLEASE_PROVIDER owner of the demo service; defaults to KEYLEASE_ADMIN public
    KEYLEASE_RATE_PER_CALL KEYLEASE_RATE_PER_CALL stroops per call, and already on-chain in service_registered public
    KEYLEASE_ENDPOINT_HASH KEYLEASE_ENDPOINT_HASH the 32-byte commitment actually stored, lowercased by the script; default sha256("<PROVIDER>:<SERVICE_NAME>") public digest, not the descriptor

    Nothing in that table is a secret. Every one of those values is either on the ledger already — visible through get_service, get_token or the service_registered event — or an address that is by definition public. So the rule is simple:

    Never commit Where it belongs instead
    The seed of any identity used here (SOURCE_ACCOUNT, admin, provider, consumer) the stellar CLI keystore, or an OS secret manager
    The off-chain endpoint descriptor behind KEYLEASE_ENDPOINT_HASH your own config; only the digest goes on-chain, and a committed descriptor is one an attacker can re-derive to confirm they guessed your service
    .env itself, and anything you add to it later — database URLs, webhook signing secrets a secret manager; .env is gitignored, .env.example is the committed template and carries no values

    Four entries in .env.example are not printed by the script, so pasting the output leaves them empty:

    • KEYLEASE_NETWORK_PASSPHRASE — the signing string for the network; the script passes --network, which reads its own CLI config, so it never needs the passphrase and never prints it. Take it from Networks.
    • SOURCE_ACCOUNT — an input, not an output.
    • KEYLEASE_GENERATE_KEY — an input, and Testnet-only.
    • KEYLEASE_CONSUMER — a consumer you fund after the deploy; the script has no reason to know it.

    The minimum env for a read¶

    After cp .env.example .env, three entries are enough to read a deployment:

    KEYLEASE_NETWORK=testnet
KEYLEASE_RPC_URL=https://soroban-testnet.stellar.org
KEYLEASE_CONTRACT_ID=C...

    Read views require no authorization and submit nothing, so no funds move and no escrow token is involved: KEYLEASE_TOKEN_ADDRESS, KEYLEASE_RATE_PER_CALL, KEYLEASE_ENDPOINT_HASH, KEYLEASE_ADMIN and KEYLEASE_PROVIDER are all unread. KEYLEASE_SERVICE_ID matters only as the thing you name — it is an argument to get_service, the way lease_id is to get_lease — and KEYLEASE_CONSUMER is never needed for a read.

    stellar contract invoke \
  --id "$KEYLEASE_CONTRACT_ID" --source-account "$SOURCE_ACCOUNT" \
  --network "$KEYLEASE_NETWORK" -- get_service --service_id "$KEYLEASE_SERVICE_ID"

    That call names one more variable, SOURCE_ACCOUNT: a local CLI identity to build the simulation against. It is an input from Configuration, not one of the printed outputs, and it is not a secret in the file either — only its address is ever written down here. A client that only reads can skip the CLI entirely and simulate directly, which needs no signing authority at all; see Integration. Note that the CLI resolves the endpoint from its own --network configuration, so KEYLEASE_RPC_URL is consumed by your own client and indexer rather than by the CLI.

    Configuration¶

    Variable Default Meaning
    SOURCE_ACCOUNT keylease-admin stellar CLI identity used to sign
    NETWORK testnet network name from your CLI config
    REGISTRY_ALIAS keylease-registry contract alias saved locally
    ADMIN address of SOURCE_ACCOUNT registry admin
    PROVIDER ADMIN owner of the demo service
    TOKEN native SAC on NETWORK escrow token
    RATE_PER_CALL 1000000 0.1 XLM at 7 decimals
    ENDPOINT_HASH sha256("<PROVIDER>:keylease-demo") 32-byte commitment
    KEYLEASE_GENERATE_KEY unset 1 to generate + Friendbot-fund the identity
    KEYLEASE_ALLOW_MAINNET unset 1 to permit NETWORK=mainnet for this invocation

    Doing it manually¶

    The script is the supported path, but the raw commands are:

    # 0. identity
stellar keys generate keylease-admin --network testnet --fund

# 1. build
rustup target add wasm32v1-none
cargo build --target wasm32v1-none --release --package keylease-registry

# 2. deploy
REGISTRY=$(stellar contract deploy \
  --wasm target/wasm32v1-none/release/keylease_registry.wasm \
  --source-account keylease-admin \
  --network testnet \
  --alias keylease-registry)

# 3. initialize
ADMIN=$(stellar keys address keylease-admin)
stellar contract invoke --id "$REGISTRY" --source-account keylease-admin \
  --network testnet --send=yes -- init --admin "$ADMIN"

# 4. configure the escrow token (native SAC here)
TOKEN=$(stellar contract id asset --network testnet --asset native)
stellar contract invoke --id "$REGISTRY" --source-account keylease-admin \
  --network testnet --send=yes -- set_token --admin "$ADMIN" --token "$TOKEN"

# 5. publish a service
stellar contract invoke --id "$REGISTRY" --source-account keylease-admin \
  --network testnet --send=yes -- register_service \
    --provider "$ADMIN" \
    --rate_per_call 1000000 \
    --endpoint_hash 0707070707070707070707070707070707070707070707070707070707070707

    --send=yes is required for the state-changing invocations. Without it the CLI only simulates. The -- before the function name is required.

    Verifying a deployment¶

    stellar contract invoke --id $REGISTRY --source-account keylease-admin --network testnet -- version
stellar contract invoke --id $REGISTRY --source-account keylease-admin --network testnet -- get_admin
stellar contract invoke --id $REGISTRY --source-account keylease-admin --network testnet -- get_token
stellar contract invoke --id $REGISTRY --source-account keylease-admin --network testnet -- get_service --service_id 1
stellar contract invoke --id $REGISTRY --source-account keylease-admin --network testnet -- service_count

    For a repeatable, pass/fail check, use the verification script. It reads the contract id from .env (or the environment), checks version, get_admin, get_token and a demo service, prints PASS/FAIL per check, and exits non-zero on mismatch:

    ./scripts/verify-deployment.sh --env-file .env
# Preview without network calls:
./scripts/verify-deployment.sh --env-file .env --dry-run

    version is embedded by contractmeta!, so it proves which release is live. The contract id itself is in the registry: see Deployments, and the explorer link for that network in Networks.

    Upgrading¶

    The contract is upgradeable in place through the Soroban deployer; the contract id, storage and balances are preserved. Because the old storage carries over, the steps must run in order and the result must be checked, so they are scripted:

    ./scripts/upgrade.sh --contract-id C... --admin keylease-admin

    Both flags are required and have no defaults: the script will not guess which contract to replace or which key signs for it. --admin is a stellar CLI identity; its address is passed to upgrade --admin and must equal the live get_admin, which the script checks before it sends anything.

    What the upgrade script does¶

    0. get_admin, version                     -> confirm the signer is the admin, record the live version
1. cargo build --target wasm32v1-none --release --package keylease-registry
2. stellar contract upload  <registry wasm> -> Wasm hash (must equal sha256 of the built file)
3. stellar contract invoke -- upgrade      --admin <ADMIN> --new_wasm_hash <HASH>
4. stellar contract invoke -- version      -> must equal [workspace.package] version in Cargo.toml

    It then prints the Wasm hash, the version before and after, and the stellar events command (with the contract_upgraded topic filter and the ledger it started from) to confirm the upgrade event. It exits non-zero when:

    • --contract-id or --admin is missing, or the id is not a C... contract id;
    • the identity is not the registry admin;
    • the live contract already reports the workspace version — bump [workspace.package] version first, or pass --allow-same-version to re-install the same release deliberately;
    • the uploaded hash differs from the local build;
    • version() after the upgrade does not equal the workspace version.
    Flag Default Meaning
    --contract-id required (env CONTRACT_ID) registry contract to upgrade
    --admin required (env ADMIN_IDENTITY) stellar CLI identity of the registry admin
    --network testnet (env NETWORK) network name from your CLI config
    --allow-same-version off proceed when the live version already equals the workspace version
    --yes off skip the confirmation prompt (required on a non-interactive shell)

    REGISTRY=C... SOURCE_ACCOUNT=keylease-admin ./scripts/deploy-testnet.sh --upgrade builds and uploads the Wasm and then queues it behind the contract's 24h time lock; --execute-upgrade installs the proposal once that delay has elapsed and --cancel-upgrade drops it.

    Upgrading manually¶

    The raw commands the script wraps are:

    # 1. upload the new Wasm and print its hash
WASM_HASH=$(stellar contract upload \
  --wasm target/wasm32v1-none/release/keylease_registry.wasm \
  --source-account keylease-admin --network testnet)

# 2. propose the upgrade (admin auth); read back the hash and execution ledger
stellar contract invoke --id $REGISTRY --source-account keylease-admin \
  --network testnet --send=yes -- propose_upgrade \
    --admin $ADMIN --new_wasm_hash "$WASM_HASH"
stellar contract invoke --id $REGISTRY --network testnet -- get_pending_upgrade

# 3. wait until ledger.timestamp() >= execute_after (24h), then install
stellar contract invoke --id $REGISTRY --source-account keylease-admin \
  --network testnet --send=yes -- execute_upgrade --admin $ADMIN

# 4. lift the post-upgrade stop (a no-op when the storage schema is unchanged)
stellar contract invoke --id $REGISTRY --source-account keylease-admin \
  --network testnet --send=yes -- migrate --admin $ADMIN

# 5. confirm the new version and schema, and watch the events
stellar contract invoke --id $REGISTRY --source-account keylease-admin --network testnet -- version
stellar contract invoke --id $REGISTRY --source-account keylease-admin --network testnet -- schema_version
stellar events --id $REGISTRY --network testnet --start-ledger <ledger>

    Guard rails for an upgrade: keep the storage layout unchanged unless you bump the storage schema and ship a migration (see Storage schema migrations), append error codes instead of renumbering, and keep event names and payload fields backwards-compatible. The execute_after timestamp and proposed hash are public via get_pending_upgrade and upgrade_proposed; announce them so clients can exit in time. Settle or revoke in-flight leases before changing token semantics. See Security and the design note.

    Storage schema migrations¶

    The registry records which storage schema its data conforms to (schema_version(), stored under DataKey::SchemaVersion), and every Wasm knows which schema it was built for (code_schema_version(), and the storageSchemaVersion metadata on the uploaded Wasm). When the two differ, the registry is stopped: set_token, register_service, set_service_active, create_lease, settle_lease and revoke_expired_lease revert, and no value can move.

    Stored vs. code State Error Way out
    equal running — —
    stored older stopped SchemaMigrationRequired (29) admin runs migrate
    stored newer (a downgrade) stopped SchemaVersionUnsupported (30) reinstall the newer Wasm; migrate refuses

    propose_upgrade, cancel_upgrade, execute_upgrade, migrate, bump_service, bump_lease and every read-only view stay available while stopped, so a bad install can always be rolled back and entries can be kept alive during the window. A registry deployed before versioning reports schema 0. Its layout is identical to schema 1, and the first migrate after upgrading to a versioned Wasm only writes the stamp.

    Proposing a migration¶

    A change that renames or retypes a DataKey variant, changes a stored struct's fields, or changes the meaning of a stored value must, in the same PR:

    1. Bump SCHEMA_VERSION in contracts/registry/src/storage.rs and the storageSchemaVersion metadata in lib.rs (a test fails if they diverge), and add a row to the version table in the SCHEMA_VERSION docs.
    2. Add the N-1 => … arm to storage::migrate_step. The arm must be bounded. It may rewrite instance storage, but it must never iterate over services or leases. Persistent entries are migrated lazily, by an accessor that reads both the old and the new shape and writes the new one on the next save.
    3. Add a test that seeds state in the old shape, asserts the registry is stopped with SchemaMigrationRequired, runs migrate, and asserts the old data reads back correctly and the registry runs again.
    4. Add a design note under docs/design/ and a release note that says the upgrade stops the registry until migrate runs.

    Changes that old entries already satisfy, such as a new key that defaults when absent, do not need a bump.

    Reviewing a migration¶

    The reviewer checks that the bump and the migrate_step arm are in the same PR, that the arm is bounded, that every old-shape value has exactly one new-shape meaning, and that the test above exists. Before installing, the reviewer confirms the uploaded artifact is the reviewed build:

    stellar contract info meta --wasm target/wasm32v1-none/release/keylease_registry.wasm
# storageSchemaVersion must equal schema_version() + 1, or equal it when no
# migration is expected

    Executing a migration¶

    1. Record the live state (step 2 of the checklist below), including schema_version.
    2. execute_upgrade, once the 24h delay after propose_upgrade has passed. From this transaction on the registry is stopped. Nothing can be created, settled or revoked, and no value moves.
    3. migrate --admin $ADMIN in the very next transaction, to keep the stop short. It runs every step from the stored version to the code's version and stamps the new version atomically, then emits schema_migrated.
    4. Verify that schema_version equals the new version and that pre-upgrade leases and services read back unchanged, then resume traffic.

    If migrate fails, the registry stays stopped and nothing is written. Reinstall the previous Wasm hash with propose_upgrade and execute_upgrade, which is valid until migrate succeeds, because the stored data is still in the old schema. The upgrade time lock still applies, so a rollback keeps the registry stopped for at least 24 hours: rehearse the migration on Testnet first. After a successful migration, rolling back to the old Wasm leaves the registry stopped with SchemaVersionUnsupported, which is the intended outcome. The old code cannot read the new data, and it must not write over it.

    scripts/deploy-testnet.sh --execute-upgrade runs execute_upgrade and migrate back to back and prints the resulting schema_version.

    Upgrading safety checklist¶

    An upgrade replaces the code but keeps the contract id, so every stored entry written by the old Wasm is still there when the new Wasm runs. The new code does not get a clean slate — it gets your users' escrow. Work the checklist in order.

    1. Invariants the new Wasm must preserve. These are the reasons the guard rails above exist; the full layout is in Storage layout.

    Invariant Why an upgrade can silently break it
    DataKey variant names and arities: Admin, Token, ServiceCount, LeaseCount, Service(u64), Lease(u64) A #[contracttype] enum key encodes as Vec[Symbol("<variant>"), …], so renaming Lease to Leases orphans every existing entry. The registry then reads LeaseNotFound on leases that still hold escrow.
    Stored value shapes for Service and Lease Entries decode by field name and type. Renaming used_calls, retyping locked_deposit, or removing settled reinterprets or loses live records.
    Field presence, not field order, for structs Old entries are read by key, so adding a field is safe only if the accessor tolerates its absence in entries written before the upgrade.
    Error codes, append-only (1–30 today) Callers and indexers branch on the number; a reused code changes what a past transaction meant.
    Event names, topics and payload fields, append-only They are the indexing ABI. Dropping a #[topic] field shifts every subscriber's filter, including the base64 segments in Topics, payloads and filters.
    LeaseStatus discriminants (0/1/2/3) Returned by lease_status and cached by clients. Revoked = 3 was appended; reusing 2 for a reclaimed lease would rewrite what every cached Settled meant.
    The settled-before-token-call ordering in settle_lease and revoke_expired_lease It is the double-payout guard; reordering it behind a transfer reintroduces the re-entrancy bug the suite proves closed.
    The lease TTL policy covers term + 24 h grace + read buffer If a shorter policy evicts a lease entry while escrow is still locked, the consumer's revoke path disappears.
    MAX_LEASE_DURATION_SECS never lowered below an in-flight lease's term Existing leases stay settleable; lowering the cap for new leases is additive, lowering it retroactively is not.

    2. Record the live state before you touch anything.

    # version, counters and the exact Wasm you are replacing
stellar contract invoke --id $REGISTRY --source-account keylease-admin --network testnet -- version
stellar contract invoke --id $REGISTRY --source-account keylease-admin --network testnet -- service_count
stellar contract invoke --id $REGISTRY --source-account keylease-admin --network testnet -- lease_count
sha256sum target/wasm32v1-none/release/keylease_registry.wasm

    Keep the highest pre-upgrade lease_id and note the current ledger: it is the --start-ledger for the replay in step 5.

    3. Upgrade. Upload, install, and keep the hash the deployer returned. ./scripts/upgrade.sh --contract-id $REGISTRY --admin keylease-admin runs this step and step 4 together; the raw commands are:

    WASM_HASH=$(stellar contract upload \
  --wasm target/wasm32v1-none/release/keylease_registry.wasm \
  --source-account keylease-admin --network testnet)
stellar contract invoke --id $REGISTRY --source-account keylease-admin \
  --network testnet --send=yes -- upgrade --admin $ADMIN --new_wasm_hash "$WASM_HASH"

    Then run migrate --admin $ADMIN (see Storage schema migrations); until it succeeds every state-changing call reverts.

    4. Compare version() and schema_version(). The embedded metadata must move; a build that did not bump the workspace version installed new code that still reports the old one.

    stellar contract invoke --id $REGISTRY --source-account keylease-admin --network testnet -- version
stellar contract info meta --id $REGISTRY --network testnet

    version must equal the release you intended, name must still be KeyLeaseRegistry, and schema_version must equal code_schema_version. Then re-read one lease and one service created before the upgrade and diff the field values against step 2 — identical expires_at, allocated_calls, locked_deposit and settled is what proves the stored shapes were not reinterpreted.

    5. Replay the events across the boundary.

    stellar events --id $REGISTRY --network testnet --start-ledger <ledger-from-step-2>

    Expect exactly one contract_upgraded carrying the new_wasm_hash from step 3, with nothing else in that transaction, followed by a schema_migrated if the storage schema moved; the counters must be unchanged across it (service_count and lease_count before equals after — an upgrade mints no leases); and every lease_created before the upgrade must still have a terminal lease_settled or lease_revoked after it. If a pre-upgrade lease that was Active now reverts on settle_lease, stop: the new Wasm is not storage-safe.

    6. Only then resume traffic, and record the outcome — the new version, Wasm hash and upgrade ledger — in Deployments, which ties a listed address to a revision.

    Rollback. upgrade is symmetric: install the previous Wasm's hash the same way. It is only safe while the new build has written nothing the old one cannot read, so a new DataKey variant or new field is a one-way door the moment it is used. The schema stamp enforces this for versioned changes: once migrate has run, the old Wasm sees a newer schema and stays stopped (SchemaVersionUnsupported) instead of misreading the data.

    Multisig admin deployment and upgrades¶

    In production, operators should configure a cold or multi-signature account as the registry admin to prevent a single compromised key from executing unauthorized contract upgrades or token modifications.

    1. Initialization with a multisig admin¶

    Any funded account can build and deploy the contract Wasm. When initializing the registry, pass the multi-signature account address (G_MULTISIG...) as the --admin parameter:

    stellar contract invoke --id "$REGISTRY" --source-account deployer \
  --network testnet --send=yes -- init --admin "$MULTISIG_ADMIN"

    Once initialized, all functions requiring admin privileges (set_token and upgrade) call admin.require_auth(), delegating authorization enforcement to the Stellar host.

    2. Multi-party upgrade workflow¶

    Upgrades with a multisig admin are coordinated through transaction envelopes:

    1. Upload the new Wasm: Any account can upload the compiled bytecode to obtain its hash:
    WASM_HASH=$(stellar contract upload \
  --wasm target/wasm32v1-none/release/keylease_registry.wasm \
  --source-account deployer --network testnet)
    1. Construct the unsigned invocation transaction:
    stellar contract invoke --id "$REGISTRY" \
  --source-account "$MULTISIG_ADMIN" \
  --network testnet \
  --build-only \
  -- upgrade --admin "$MULTISIG_ADMIN" --new_wasm_hash "$WASM_HASH" > upgrade_tx.xdr
    1. Collect signatures from signers: Each required co-signer signs the envelope until the cumulative signature weight meets or exceeds the admin account's threshold:
    stellar tx sign --network testnet --source-account signer-alice upgrade_tx.xdr > signed_1.xdr
stellar tx sign --network testnet --source-account signer-bob signed_1.xdr > signed_threshold.xdr
    1. Submit the fully-signed transaction:
    stellar tx send --network testnet signed_threshold.xdr

    Host-level auth guarantees¶

    • What the contract enforces: The contract checks admin.require_auth(). If the accumulated signature weight does not meet the Stellar account's configured threshold, the host rejects the transaction before contract invocation occurs.
    • What the contract cannot enforce: The contract does not inspect individual signer identities, weights, or whether the signer set is 2-of-3 versus 1-of-1. Those rules live entirely within the Stellar account configuration.

    Post-deploy¶

    1. Fund a consumer so create_lease can escrow a deposit.
    2. Point your client or indexer at the registry with KEYLEASE_CONTRACT_ID, KEYLEASE_RPC_URL and KEYLEASE_NETWORK.
    3. Subscribe to events, or read get_lease on demand — see Integration.
    4. Optionally run the smoke test after deployment to confirm the contract can escrow and settle a one-call lease on the selected network. It is opt-in and guarded to avoid accidental production runs:
    KEYLEASE_SMOKE_TEST=1 \
CONSUMER_IDENTITY=keylease-consumer \
PROVIDER_IDENTITY=keylease-admin \
KEYLEASE_CONTRACT_ID=C... \
KEYLEASE_SERVICE_ID=1 \
KEYLEASE_TOKEN_ADDRESS=C... \
./scripts/smoke-test-deployment.sh --env-file .env

    Use --dry-run to print the planned commands without sending transactions. Set KEYLEASE_SMOKE_VERIFIED_CALLS=0 or 1 to control settlement; 1 is the default. The script prints create/settle transaction output and exits non-zero on failure. Mainnet requires both KEYLEASE_NETWORK=mainnet and KEYLEASE_ALLOW_MAINNET=1.

    Networks¶

    Testnet, Futurenet, Mainnet and local standalone differ only in RPC endpoint and passphrase; the full table, SAC addresses and reset schedule are in Networks.

    Mainnet¶

    Not yet. Mainnet deployment is deferred until the contract is audited — see Security and the known limitations listed there. The deploy script enforces this: NETWORK=mainnet is refused unless KEYLEASE_ALLOW_MAINNET=1 is set explicitly, and a --dry-run never sends anything even then.
